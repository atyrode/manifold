# Terminal quality investigation — first-session evidence

Dates: 2026-09-05 (experiments 1–5); 2026-09-26 (phase-2 experiments 6–9 and operator options). Investigation: [#281](https://github.com/atyrode/manifold/issues/281).

## Decision summary

Keep the current terminal engine while isolating sizing, shared-PTY authority, replay ordering, and flow control. The completed browser experiment demonstrates a host/FitAddon box-model integration mismatch. The completed transport experiment demonstrates that two distinct connections of the same principal can alternately resize the actual shared PTY. Neither result establishes the cause of the user's duplicated TUI lines, nor establishes an engine performance bottleneck.

This is research, not a native-parity claim. The complete beta combines terminal fitting/publication fixes with a separate shared-tile fix: ratio-only layout changes must not animate the scale of live contents. Experiments 3–4 describe the **intermediate terminal-only beta**, which still stretched during dragging; experiment 5 isolates and corrects that regression. Deployment status belongs to [#284](https://github.com/atyrode/manifold/issues/284), not an inference from source presence. The user's Mac/PC repeated-redraw reports remain unresolved. The companion [terminal quality contract](terminal-quality-contract.md) owns desired outcomes and acceptance obligations; [#281](https://github.com/atyrode/manifold/issues/281) stays open for the broader program-neutral initiative.

Evidence labels distinguish **completed observations**, **source findings**, **hypotheses**, and **recommendations**. A matched continuous-drag browser comparison and pinned engine feasibility replay completed. They are not an engine performance ranking. No native Ghostty comparison, physical-display latency, or uncontended performance baseline is reported here.

**Phase 2 (2026-09-26).** [Experiments 6–9](#phase-2-non-native-measurements-2026-09-26) measured the remaining non-native questions on disposable loopback instances. Transport resize ordering is correct. The duplicate-row mechanism reproduced is a relative-redraw program meeting terminal reflow — one stale block per shrinking resize — multiplied by the same-principal size fight: a divider drag on one device makes both devices publish, and the non-owning device is letterboxed or clipped. Two ordering gaps make live and reloaded views disagree. A slow device does not slow others, but a slow parser has no upstream flow control, and an overflowing viewer silently loses scrollback to a resnapshot. DOM rendering, not parsing, dominated browser cost under heavy output. That section ends with size-ownership and renderer options and the on-device questions the operator owns; no product code changed.

## Completed experiment 1: browser bottom-edge geometry

This was a manual browser experiment, not an automated benchmark. Session record:

| Variable                            | Observed value                          |
| ----------------------------------- | --------------------------------------- |
| Source revision / runtime version   | `629f91a` / `v0.7.0`                    |
| Host / runtime                      | Linux `6.18.34`, Bun `1.3.13`           |
| Browser                             | Chromium `148`                          |
| CSS viewport / device pixel ratio   | `1440 × 900` / `1.25`                   |
| Composition / terminal font size    | Solo / `13`                             |
| Host bottom / height                | `900` / `834.406` CSS px                |
| Host padding                        | `5.6` CSS px                            |
| xterm screen height / rows / bottom | `832` CSS px / `52` / `903.1875` CSS px |

**Observation:** the xterm screen extended `3.1875` CSS px below the host bottom. Removing **only the host padding at runtime** retained the same `52` rows and moved the screen bottom to `897.59375`, inside the host. The temporary override was removed afterward, restoring the original styling. This intervention did not change the renderer, transport, font size, or product code.

**Source explanation at baseline `629f91a`:** [`styles.css`](../../packages/plugins/terminals/src/styles.css) gave `.xterm-host` `box-sizing: border-box`, `padding: 0.35rem`, and clipped overflow; its child `.xterm` had `height: 100%`. The inspected FitAddon `0.11` source, lines 72–85, uses the parent’s computed height but subtracts the terminal element’s padding, which was `0` in this experiment ([upstream FitAddon source](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-fit/src/FitAddon.ts); the inspected package version is the evidence, not a claim that mutable upstream line numbers are fixed). The beta margin change addresses this demonstrated mechanism; this baseline observation does not by itself verify the changed product across sizes.

Together, the measured intervention and sizing algorithm demonstrate a **box-model integration mismatch**, not proof that xterm intrinsically cannot fit. The observed fit at font size `32` is coincidental row quantization: coarser rows can leave enough remainder to hide a padding error. It is not evidence that the sizing contract is correct at other sizes. The retained row count after padding removal also shows why checking only `rows`/`cols` misses the visible defect.

**Boundary:** this establishes one geometry mechanism at this viewport/DPR/font condition. It does not establish the full divider-drag timeline, all zoom modes, platform rasterization behavior, or the source of repeated TUI lines. Browser zoom, OS scaling/DPR, terminal font zoom, and pane resizing must be separate conditions.

## Completed experiment 2: real PTY and two same-principal SDK sockets

Command for the three standalone runs: `BENCH_RTT_SAMPLES=30 BENCH_RESIZES=20 bun scripts/bench-terminal-transport.ts`. Raw evidence: [run 0](terminal-quality-data/transport-0.json), [run 1](terminal-quality-data/transport-1.json), [run 2](terminal-quality-data/transport-2.json).

The research script creates its own temporary loopback server, enrolled agent, principal grant, composition, and real PTY fixture. Two canonical SDK clients use distinct WebSocket factory identities to bypass pooling, authenticate with the same grant, and explicitly verify both same-principal and distinct-transport identities. This is not two handles sharing one socket and not a mocked PTY. No production session is used.

### Correctness observations

- Each of the **three** runs confirmed two real, distinct SDK sockets with the same principal.
- Each accepted **20** alternating `96 × 28` / `132 × 40` requests: **60 actual-PTY resizes** total. The fixture handles `SIGWINCH`, queries `stty`, and emits a geometry marker; this goes beyond a broker metadata acknowledgment.
- Each completed **30** alternating input samples; observed output sequences were contiguous.
- In each run both viewers received the **139,180-byte**, **512-marker** batch exactly, with expected SHA-256 equality and marker ordering.
- All three runs reported correctness `ok: true`, with no failures or errors.

These observations prove acceptance of competing same-principal size authorities for the bounded alternating workload. They do **not** reproduce simultaneous cross-device drag, demonstrate duplicate rendered rows, or identify the root cause of the user's duplicated UI. Serialized snapshot correctness and byte continuity do not imply correct browser reflow at a different grid.

## Completed experiment 4: induced stale-echo ordering

An older `terminal_event resized` can call `terminal.resize(oldCols, oldRows)` after the host fit but before publication. Reading only the mutable xterm grid then loses the intended final geometry.

The controlled browser experiment registered a later ResizeObserver, verified that the product had already fitted the new box, then performed that exact handler operation. It collected actual outgoing resize frames and queried the real PTY with `stty size`. A one-call ablation suppressed only the new publication-time fit, keeping the earlier ResizeObserver fit intact:

| State                                           | Publication-time fit enabled | Only that fit suppressed |
| ----------------------------------------------- | ---------------------------- | ------------------------ |
| Previously published grid                       | `136 × 51`                   | `136 × 51`               |
| New host's proposed grid / observed initial fit | `131 × 51`                   | `131 × 51`               |
| Injected stale grid                             | `136 × 51`                   | `136 × 51`               |
| Outgoing correction                             | Exactly one `131 × 51`       | None                     |
| Settled rendered grid                           | `131 × 51`                   | Stale `136 × 51`         |

The real PTY printed `RACE_GRID 51 131` (rows, then columns) for the corrected case. [Raw ordering evidence](terminal-quality-data/race-order.json). Instrumentation and the temporary width override were removed afterward. This isolates why the added fit is necessary; it is not a natural network-echo trace or a measurement of the race's frequency. It does not change ownership or filter arbitrary “old” output.

## Completed experiment 5: visual divider-resize regression

The operator emphasized that stretching was a **regression**, not an acceptable browser limitation. Source history separates it from the long-standing PTY delay: `75eb186` introduced `TileMotionBoundary`, whose pre-mutation snapshot ran for every new layout object, including continuously changing ratios. Its FLIP animation scaled the live terminal contents after each divider update. The preceding renderer directly seated stable hosts without those animations.

A real 20-step mouse drag against the intermediate beta retained both rAF geometry samples and a held-drag screenshot. A separate run used the complete fix (`index-NBScF-9-.js`):

| Held host samples                             | `110`                  | `68`           |

[Before trace](terminal-quality-data/stretch-before.json), [after trace](terminal-quality-data/stretch-after.json), [before screenshot](terminal-quality-data/stretch-before-held.png), [after screenshot](terminal-quality-data/stretch-after-held.png). The screenshots contain sparse prompts, so the numerical glyph/transform trace is stronger evidence of distortion than letter-shape inspection. One screenshot was taken mid-drag in each run: this is a visual correctness experiment, not a cadence or native-latency comparison.

The fix reuses the existing `layoutRevision` definition of **structure and occupancy, excluding proportions**. Ratio-only updates do not start settlement animation and cancel interpolation left from a previous settlement; structural placement and carry previews retain their existing animation. There is no local/remote branch and no terminal-specific exception in the shared tile renderer.

A permanent browser-boundary check in `verify-tile-drop.ts` drives ratios from an SDK producer while the receiving browser samples every frame. Against the intermediate bundle it failed with **31/33 moved frames**, despite actual layout width changing from `557` to `735 px`. Against the complete bundle it passed with **0/33 moved frames** over the same width change. The rest of the tile-drop gate also passed, including structural motion, transform-without-PTY-reflow during previews, stable xterm hosts, cancellation, multiplayer equivalence and engaged-portal divider interaction.

The complete bundle also finished the combined UI diagnostic with exit 0, 149 trusted intended clicks, 29 captures and successful cleanup. It sent **38 resize frames during the held drag (19 per terminal)**, with the final sizes sent about **34 ms before release**, and none afterward through the settled capture. Font-13 screens remained `7.21875 px` inside their hosts. [Complete-run JSON.gz](terminal-quality-data/ui-final.json.gz). This run is separate from, and does not overwrite, the intermediate results.

The intermediate PTY-update A/B was therefore necessary but **insufficient** evidence for the user's visible complaint. This record preserves that distinction rather than retroactively claiming the first fix solved stretching.

### Completed experiment 6: causal resize ordering through server, agent and viewers

Two same-principal SDK sockets (A, B) on distinct transports attach one PTY fixture. `single` = A publishes 40 sizes 16 ms apart (one publication per frame, like a held drag); `dual` = A and B each publish 40 sizes concurrently (two devices fighting); `none` = same duration without resizes. A late attacher C then receives the agent mirror's snapshot. Viewer behavior is reproduced by replaying each captured stream through xterm with `write("", () => resize())` at the exact stream position where the `resized` event arrived, which is TerminalView's ordered path. Workloads: **stream** — a line every 2 ms tagged with the grid the program believes, each exactly `cols − 1` wide; **inline** — a 6-row block redrawn after SIGWINCH by relative cursor-up + erase-down, the way inline TUIs redraw; **anim** — the same block also re-rendered every 16 ms (a spinner). Five repetitions per cell.

| Workload / writers | Accepted resizes per repetition | Stale-grid lines at A (5 repetitions) | Stale window max (ms) | `resized` → first new-grid PTY byte, p50 / max (ms) | Block copies, live A / snapshot C             | Live buffer = snapshot |
| ------------------ | ------------------------------- | ------------------------------------- | --------------------- | --------------------------------------------------- | --------------------------------------------- | ---------------------- |
| stream / none      | 0                               | 0 of 641–654 each                     | –                     | –                                                   | –                                             | 5/5                    |
| stream / single    | 40                              | 11, 25, 14, 20, 12 of 637–650         | 2.7–5.7               | 2.0–2.8 / 3.5–6.7                                   | –                                             | 5/5                    |
| stream / dual      | 80                              | 22, 15, 17, 37, 44 of 615–643         | 3.3–8.3               | 2.0–2.5 / 3.6–8.8                                   | –                                             | 5/5                    |
| inline / none      | 0                               | –                                     | –                     | –                                                   | 1/1 in all 5                                  | 5/5                    |
| inline / single    | 40                              | –                                     | –                     | –                                                   | **21/21 in all 5** (20 shrinking transitions) | 5/5                    |
| inline / dual      | 80                              | –                                     | –                     | –                                                   | 42/42, 31/36, 41/39, 28/30, 31/31             | 1/5 (screens 5/5)      |
| anim / none        | 0                               | –                                     | –                     | –                                                   | 1/1 in all 5                                  | 5/5                    |
| anim / single      | 40                              | –                                     | –                     | –                                                   | 24/23, 25/21, 21/21, 21/21, 21/21             | 3/5 (screens 4/5)      |
| anim / dual        | 80                              | –                                     | –                     | –                                                   | 32/32, 42/41, 53/43, 46/43, 32/32             | 1/5 (screens 3/5)      |

- **Transport ordering is correct.** In all 30 resizing repetitions A and B received identical `resized` sequences, the PTY's own SIGWINCH observations were an order-preserving subsequence of them (after collapsing back-to-back signals whose handler already read the newer size), output sequences were contiguous, and the final `stty` size equalled the last `resized` event at A and B, the server's terminal record and the late attacher's grid.
- **Stale-grid bytes are routine.** The server broadcasts `resized` when it forwards the command, before the PTY applies it, so every viewer parses bytes the program produced for the previous grid after switching grids: 11–25 lines per 40 accepted resizes (single) and 15–44 per 80 (dual), each window closing within 2.7–8.3 ms on loopback. The first byte produced for the new grid arrived 2.0–2.8 ms (p50) after the `resized` event.
- **Duplicate rows are produced at the first boundary, by resize count.** With the relative-redraw workload every shrinking column transition left exactly one stale copy of the block in the buffer: **21 copies after 20 shrinking transitions in 5/5 single-writer repetitions**, live and snapshot alike. The program erases the rows it wrote, xterm reflows those rows into more rows at the narrower width, and the difference remains. Two writers fighting produced 28–53 copies. This reproduces a duplicate-redraw mechanism without any transport fault; the number of duplicates is governed by how many shrinking resizes the PTY receives.
- **The agent mirror can disagree with live viewers.** The server's broadcast position and the agent's resize position differ by the bytes in flight between them. With two writers, or with a program writing while resizing, the late attacher's snapshot differed from the emulated live viewer's buffer in 4/5 (inline dual), 2/5 (anim single) and 4/5 (anim dual) repetitions, e.g. 53 live vs 43 snapshot copies. A serialization control (`replay(serialize(live))`) reproduced the live buffer in every repetition, so the difference is in mirror state, not in the serializer. Screens usually matched; scrollback did not. A reloaded or newly attached device can therefore show different history from a device that stayed live.

Boundary: SDK callback and headless-emulation endpoints only; no paint. Loopback transit is far shorter than a WAN, where the stale-grid window grows with one-way delay.

Two Chromium instances share one human grant and one split composition: "wide" 1440×900 at DPR 1.25 and "narrow" 1000×680 at DPR 2. The left terminal runs the inline relative-redraw fixture; the right is a plain shell. A scripted sequence of ordinary device actions ran with 900 ms settle per step. "Published" counts outbound `terminal_resize` frames observed over CDP; "shows" compares each device's xterm grid with the grid its own host would fit.

| 9   | narrow reloads                                      | 0 / 1                     | 35×40                | 6 rows, 12 cols unused  | fitted                      | 17 / 18 / 18                                |

| 11  | wide font −1                                        | 1 / 0                     | 33×51                | fitted                  | **9 rows, 7 cols clipped**  | 27 / 27 / 28                                |

Ten sessions of this sequence (one idle program, nine with the 16 ms spinner) gave the same pattern:

- **Every size-changing action on either device takes the PTY grid**: first mount, reload, font change and window resize each published once and resized the PTY; focus/click did not. Nothing a user sees distinguishes "my device owns the grid" from "the other device does".
- **A divider drag on one device makes both devices publish.** Pane ratios are shared layout, so the non-dragging device's host changes too and its ResizeObserver publishes its own fit: per 24-move drag, the dragging device published 17–21 times and the other device 12–21 times. The final grid belonged to the non-dragging device in 7/10 sessions, leaving the dragging user letterboxed.
- **The non-owning device either wastes space or loses content.** Observed states: up to 14 unused rows and 24 unused columns, or content **clipped by up to 11 rows and up to 15 columns** — the bottom rows, where prompts and cursors usually are, fall outside the host. The contract's C1 requires a deliberate local viewport or scroll affordance instead.
- **Duplicate rows accumulate with every size change**: 2 → 27 copies of the inline block over the session above. Even with the program idle between resizes, the two devices and a fresh snapshot disagreed after the drag (17 / 16 / 18).
- **With a spinner running, devices and snapshot diverge further**: in one uninstrumented session the two live devices gained 33 and 26 blocks during the same concurrent step from the same byte stream, ending at 60 and 51 against 43 in a fresh snapshot. Two causes were measured. (1) Experiment 6's mirror position. (2) TerminalView applies `resized` on two paths: the ordered `terminal.write("", () => terminal.resize())` and an effect on the SDK's terminal record ([`terminal-view.tsx`](../../packages/plugins/terminals/src/terminal-view.tsx), the `[terminal]` effect) that resizes immediately, ahead of unparsed bytes. The instrumented resize wrapper counted 4–22 such out-of-order applications per session, 2–8 of them with unparsed bytes pending (at most 1,158 bytes). With those applications suppressed in-page (ablation; the ordered path still applies the same size), the two live devices never diverged (0 of 4 sessions); without suppression they diverged at least once in 4 of 6 sessions (2 of 4 instrumented, both uninstrumented). The mirror differed from both live devices after the drag in 8 of 8 instrumented sessions either way. This is consistent with, not a statistical proof of, the effect path causing live-device divergence.

Boundary: headless Chromium, software raster, synthetic pointer input, two devices on one host. A CDP page-lifecycle freeze was attempted and rejected as a harness condition: afterwards `requestAnimationFrame` never fired again in headless Chromium, even after reload, so post-freeze publication counts are harness artifacts, not product behavior.

### Completed experiment 8: slow readers and parser backlog

One terminal runs a paced producer of SGR-colored ~80-column log lines with a timestamped marker every 20 ms. Viewers: an SDK socket F (transport arrival only), a normal Chromium TerminalView V1, and a second TerminalView V2 made slow by CDP CPU throttling (4× or 20×) or by stalling its main thread in the debugger (`Debugger.pause`, no JS runs until resumed at the end of production). Every 250 ms a real CDP keystroke is sent alternately from V1 (Ctrl+K) and V2 (Ctrl+]; skipped while stalled); the fixture echoes each as a timestamped marker. Rates: 256 KiB/s (log), 2 MiB/s (heavy), unpaced (flood, 20–28 MiB/s at F); three repetitions each. "Parse lag" = xterm write-callback time − producer timestamp; "key → echo" = page keydown → echo marker parsed in the same page. In-page counters replace CDP network capture, which would copy every payload to the harness under load.

- **A slow device does not slow anyone else.** Across all 51 runs, F's producer-to-arrival lag stayed at p50 0.2–0.6 ms (p95 ≤ 6.1 ms) for paced output and p50 1.2–1.9 ms (p95 ≤ 7.6 ms) unpaced, and at 256 KiB/s and 2 MiB/s the normal browser V1 kept parse-lag p50 0.7–2.3 ms and key → echo p50 10.6–14.5 ms (p95 ≤ 40 ms) whatever V2 was doing. Server fan-out is per channel; the server's resident memory peaked at 147–232 MB over these runs.
- **The server bound works and is the only end-to-end bound.** A viewer that stops consuming (stalled, or too slow at 2 MiB/s) is cut off by its channel queue (256 frames / 1 MiB, [`session-channel.ts`](../../packages/server/src/session-channel.ts)) with `channel_closed` 1013 "outbound queue overflow"; the web client rejoins and receives a fresh snapshot. Recovery was fast (0.3–0.65 s after a stall ended), but output between the overflow and the snapshot is never delivered live: only 78–158 of 400 markers were parsed live and 3–6 more surfaced only inside the snapshot. The result is truthful but lossy for scrollback; nothing tells the user that history was skipped.
- **A slow parser has no upstream flow control.** At 20× CPU and 256 KiB/s the page kept draining its socket (arrival lag p50 0.23–0.53 s, no overflow) while xterm's own write queue grew to 1.5–1.9 MB: parse lag reached 16.6–21.5 s and that device's own keystrokes echoed 7.7–14.1 s late (p50). Latency grows without bound until either xterm's 50 MB discard watermark throws (`WriteBuffer.ts`, not reached here) or the device stops draining its socket. This is the gap the investigation hypothesized; it is now measured.
- **Unpaced output overwhelms even a normal browser on this host.** At 20–28 MiB/s the unthrottled V1 was itself cut off 0–5 times per 6-second run, parsed 190–300 of 300 markers live, and echoed keystrokes after p50 44–810 ms. Arrival lag (p50 33–152 ms) dominated its parser queue (p50 ≤ 2.4 ms): the main thread, not xterm's parser, was saturated. Experiment 9 attributes most of that to rendering.
- Load sensitivity: an earlier smoke run of the 4× CPU, 2 MiB/s condition at 1-minute load ≈ 15 (not retained as evidence) showed V2 parse lag p50 3.9 s and two overflow closes, versus 60–86 ms and none at load ≈ 6–10. Thresholds, not just magnitudes, move with contention; physical-device measurements are needed before any budget.

### Options for the operator: size ownership

The measured problem is not ordering at the transport, which is correct, but **who may change the one PTY grid**. Today every connection of the controlling principal is an equal size writer.

| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **A — keep principal-wide last writer** (status quo)              | Any same-principal connection whose host box changes publishes; last accepted wins.                                                                                                                                                                                                                                                                                                                                                                                                                                        | Measured above: mount, reload, font, window change and divider drag on either device take the grid; one drag produced 29–42 accepted resizes from two devices; the dragging device ended letterboxed in 7/10 sessions; the other device clipped up to 11 rows / 15 columns; one duplicate inline block per shrinking resize.                                                   | No work. Leaves the operator-reported fight and its duplicates.                                                                   |
| **B — per-connection size lease within the controller principal** | Exactly one connection publishes geometry. The lease moves only on deliberate use of another device (keyboard input into that terminal, or an explicit "fit to this device" action), never on mount, reload, font, window or shared-layout change. Independently of the choice, two causal-ordering defects are fixable without deciding ownership (recorded here as findings, not implemented): TerminalView's second, out-of-order resize path, and the mirror resizing at a different stream position from viewers (a geometry epoch carried with `resized` and applied at a defined output sequence would make both agree).

### Remaining on-device questions for the operator

Linux headless evidence cannot answer these; each is a short check on the operator's own Mac and PC foreground browsers against a disposable development terminal, with native Ghostty on the same machine as a separately labeled reference.

1. **Decision: size ownership A, B or C** (above).
2. **Decision: renderer keep or evaluate** (above).
3. **Clipping and theft on real devices.** With both devices on one test terminal, drag a divider on the Mac: does the PC show its bottom rows cut off, or does the Mac end letterboxed? Then change font size on the PC and reload it: does the Mac's grid change each time? Expected from experiment 7: yes to each.
4. **Duplicates: Manifold or program/reflow?** In one terminal on one device, run the operator's usual inline TUI (e.g. an agent CLI at its prompt) and narrow the pane three times. Count duplicated UI blocks in scrollback, then repeat the same three narrowing steps in native Ghostty on the same machine with the same program. Equal counts mean the duplicates are the program/reflow interaction amplified by resize count (experiment 6); more in Manifold means an additional Manifold cause.
5. **Flood responsiveness.** Run `seq 1 3000000` in a test terminal and type during it: roughly how long until the keystroke echoes, and does the tab stay responsive? Compare with Ghostty. This calibrates experiment 8's headless numbers.
6. **GPU availability for a renderer A/B.** Report whether `chrome://gpu` (or the browser's equivalent) shows WebGL2 hardware-accelerated on each device, plus browser/OS versions, display refresh rate and scaling.

### Completed pinned engine feasibility replay

[Raw engine evidence](terminal-quality-data/engine-run.json) records published **xterm 6.0.0**, **WebGL addon 0.19.0**, and **ghostty-web 0.4.0**, dependency integrity, implementation sources and Chromium `148.0.7778.215`. This isolated synthetic replay used no Manifold transport, PTY, network stream, native Ghostty, or production terminal.

- xterm DOM and ghostty-web Canvas2D each completed **six trials**, three at `80 × 24` and three at `132 × 40`. Each trial replayed `10,446` or `10,447` UTF-8 bytes: 240 colored scrolling lines followed by cursor redraw, wide and combining text. Both passed public-buffer end-marker and cursor-redraw assertions in every trial.
- xterm preserved `e` plus combining acute in all six public-buffer checks. ghostty-web's public-buffer translation returned `e` without the acute in all six, failing that assertion. **This establishes a public-buffer text discrepancy, not visible glyph loss**: visual inspection of the retained [xterm](terminal-quality-data/xterm-dom-80x24.png) and [ghostty-web](terminal-quality-data/ghostty-canvas2d-80x24.png) screenshots found a visible acute accent in both. Copy/selection behavior was not exercised, so those consequences remain to be tested. Do not silently classify the run as full correctness parity.
- xterm's callback follows parser processing; ghostty-web 0.4.0 writes synchronously to Wasm and schedules its callback with `requestAnimationFrame`. Recorded callback spans therefore have different endpoints and are **not comparable parser-latency rankings**. There was no warmup/statistical-significance or physical-paint claim.
- WebGL2 initialization refused under `--disable-gpu` with `WebGL2 not supported null`. There are **no WebGL performance numbers and no context-loss/fallback test result**. This software/headless configuration cannot decide GPU renderer quality.
- Synthetic ArrowUp encoding and input-hook introspection are not native keyboard, IME, or assistive-technology verification. The bounded replay leaves real-TUI compatibility, reflow, selection, accessibility, CSP and recovery obligations open.

Retain one integration unless evidence justifies a replacement. Prefer an upstream wrapper fix over a fork. A fork would require an immutable base, small explicit delta, upstreaming path, owner and update policy; owning a new browser terminal layer or a Ghostty ABI patch is a separate commitment, not a quick performance fix.

## Prioritized recommendations

1. **P0 — correct fit and live resize.** The bounded beta now has matched browser A/B, inspected screenshots, all-integer 8–32 font sweeps at two DPR/viewport conditions, and induced stale-echo ordering evidence. Deliver it through #284 and verify development. Real Mac/PC interaction, browser zoom and broader redraw correctness remain open; the local results are not native-parity certification.
2. **P0 — decide input authority separately from a size lease.** Resolve the policy in [#204](https://github.com/atyrode/manifold/issues/204): shared input permission must not implicitly make every same-principal connection an equally authoritative size writer. Specify lease identity/lifecycle, transfer, disconnect and spectator behavior, and what non-owning viewports display. The transport run demonstrates why this decision is necessary; it does not select the policy. [#204](https://github.com/atyrode/manifold/issues/204) has since settled input authority per principal; size ownership remains the separate decision presented in [Options for the operator: size ownership](#options-for-the-operator-size-ownership), with phase-2 measurements.
3. **P0 — geometry epoch/order and replay correctness.** Trace PTY bytes, output sequence, accepted geometry, mirror drain, snapshot watermark and browser writes through resize/reattach. Make any eventual protocol change preserve an explicitly ordered grid and output history. Diagnose repeated lines by finding the first boundary where duplication appears, not by hiding rows or discarding unproven “duplicate” data. **Phase 2:** the first duplicating boundary measured is program redraw against terminal reflow at each shrinking resize (experiment 6); live/replay divergence traces to the mirror's resize position and TerminalView's unordered resize path (experiments 6–7). A geometry epoch that ties `resized` to an output sequence, applied identically by mirror and viewers, is the indicated fix; it is recorded, not implemented.
4. **P0 — bounded end-to-end flow.** Inventory existing queue bounds and failure recovery, then exercise slow readers, parser backlog, reconnect and sustained output. Design parser-completion-aware flow only from measured queue behavior; xterm’s [flow-control guide](https://xtermjs.org/docs/guides/flowcontrol/) explains why `write` completion and PTY pause/resume/ACK watermarks matter. Do not claim the current exact-byte batch proves saturation safety. **Phase 2:** experiment 8 measured slow readers, parser backlog and overflow recovery. The missing pieces are parser-completion-aware flow control and an explicit notice when a resnapshot skips history.
5. **P1 — renderer A/B after the integration diagnosis.** Extend the completed bounded DOM/ghostty-web feasibility replay with actual copy/selection checks for the public-buffer combining-text discrepancy and real-TUI traces. The retained screenshots render the accent in both engines. Retry WebGL on a suitable GPU configuration, including forced context loss/fallback; the refused initialization is not that test. Compare correctness first and parser/scheduling endpoints separately. No product migration or dependency addition is recommended on the present evidence. **Phase 2:** experiment 9 attributes 29–43% of main-thread time at 2–6 MiB/s, and the overflows under unpaced output, to DOM rendering rather than parsing; the [renderer options](#options-for-the-operator-renderer) recommend an on-device WebGL A/B, still not an engine replacement.
6. **P1 — broader shell and file workflow quality.** Use the quality contract for selection/copy/paste, links, shell cwd and prompt/command integration, keyboard/IME, Unicode, search/scrollback, accessibility, file upload/download and drag/drop expectations. Clipboard is one dimension, not the whole investigation. Distinguish shell-provided metadata from heuristics, user-authorized file transfer from terminal byte input, and local browser files from remote paths. No implementation completeness or browser/native equivalence has been measured here.

## Reproduction commands and evidence discipline

Run research scripts **serially**, with no gates, compiler, builds, or other benchmark competing during the measurement window. These commands are runnable entry points, not claims that every entry point has completed successfully:

```sh
bun scripts/bench-terminal-transport.ts
bun scripts/bench-terminal-ui.ts --help
bun run changelog:generate
BENCH_TERMINAL_REPORT=/tmp/terminal-ui.json BENCH_TERMINAL_KEEP=1 bun scripts/bench-terminal-ui.ts
```

Both experiments target their own localhost infrastructure, not a production endpoint. The transport script requires installed repository Bun dependencies and POSIX `stty`. It supports bounded `BENCH_RTT_SAMPLES`, `BENCH_RESIZES`, `BENCH_BULK_LINES`, `BENCH_BULK_WIDTH` and `BENCH_TIMEOUT_MS` overrides; defaults are `20`, `12`, `512`, `256` and `10000` respectively.

Phase-2 experiments 6–9 used a throwaway harness that is not committed. The [phase-2 data file](terminal-quality-data/phase2-2026-09-26.md#reproducing) records the fixtures verbatim, the in-page instrumentation and the exact conditions needed to rebuild it on the same repository primitives (`scripts/cdp.ts`, `packages/testkit`, the SDK and a production web bundle).

The UI diagnostic requires Chromium and repository dependencies; generate the in-app changelog in a fresh checkout before building. `MANIFOLD_CHROMIUM` selects the browser. `MANIFOLD_GATE_DIST` can reuse an existing build; without it, the diagnostic prepares an isolated bundle before measurement. A reused bundle and server must agree on `MANIFOLD_VERSION`, `MANIFOLD_BUILD` and `MANIFOLD_CHANNEL`. `BENCH_TERMINAL_REPORT` selects the atomically written raw JSON file; stdout is a bounded summary naming it, not the full record. `BENCH_TERMINAL_KEEP=1` retains screenshots in the recorded artifact directory while server data and browser profiles are still cleaned. Earlier cleanup, mixed-build and truncated-output failures remain invalid attempts; the matched, complete runs above supersede them without treating their timing as valid evidence.

Retain each run’s JSON separately with source commit, runtime version, timestamp, workload parameters, units, raw samples, counts, correctness failures and environment. Record browser version/flags, viewport/DPR/zoom, font, renderer, CPU/GPU/display/refresh/power state, topology and contention where relevant; an absent value is unknown, not an inferred default. Never retain access tokens, owner keys or production terminal content. The short source/runtime pair above identifies the manual browser observation, not an invented complete metadata record for other runs.

Endpoints must stay distinct:

- SDK output callback: transport arrival, no browser rendering.
- xterm write callback: parser completion, not display presentation.
- DOM text or geometry observation: browser state, not physical paint.
- `requestAnimationFrame`: next render opportunity, not proof of scan-out ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)).
- Event Timing: rounded browser interaction timing with event/threshold constraints ([specification](https://www.w3.org/TR/event-timing/)); not a hardware input timestamp.
- Physical input-to-photon: requires calibrated camera/photodiode and actual input/display references. No such measurement was performed.

## Network and browser limits versus fixable integration

**Theoretical network constraint:** when a visible response depends on remote PTY processing, input must traverse the outbound path and output the return path, plus server/agent processing and browser presentation. RTT, jitter, queueing and application work therefore bound the achievable remote response; changing a parser cannot remove that transit. No numeric WAN lower bound or one-way delay was measured here. Do not subtract timestamps from unsynchronized Mac/PC clocks; measure same-clock round trips or clearly defined individual legs.

**Documented browser constraints:** [clipboard](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API) access depends on secure contexts, permissions/user activation and browser differences. OS/browser-reserved shortcuts and [IME composition](https://developer.mozilla.org/en-US/docs/Web/API/Element/compositionstart_event) are not equivalent to raw native terminal key events. Browser file access requires user authorization; a local browser path is not a remote-agent filesystem path. Background scheduling throttles timers and pauses most rAF work ([Chrome policy](https://developer.chrome.com/blog/background_tabs)). These are platform constraints to design around, not measurements of current Manifold failures. Permissions, clear affordances and application wiring still remain fixable product responsibilities.

**Actual Mac/PC display tests are required.** This Linux/Chromium evidence cannot clear native macOS or PC GPU/compositor behavior, physical refresh/VRR, font rasterization, keyboard layouts, dead keys/IME, clipboard prompts, file dialogs or physical latency. Repeat sizing, real-TUI redraw, input, selection and file/shell workflows on the intended foreground browsers and physical displays, then repeat the shared terminal with the intended network topology. Compare native Ghostty on each same host only as a separately labeled native/local-PTY baseline. No native-parity conclusion follows from localhost bytes, headless timing, or the choice of parser library.
