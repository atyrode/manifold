# Proposed terminal quality contract

**Status: operator proposal, not ratified architecture or an implementation claim.** This is the desired non-negotiable capability list for [#281](https://github.com/atyrode/manifold/issues/281). It does not amend [CONTRACTS.md](../CONTRACTS.md), add a floor/pillar, select a renderer, authorize deployment, or disturb [#278](https://github.com/atyrode/manifold/issues/278)'s independent agent-preservation work. Terminal remains a plugin; its quality is a product priority.

The operator's zoom-bottom overflow, divider lag/stretch, competing Mac/PC geometry and duplicate-redraw reports are accepted defects. Their causes remain to be isolated. Neither browser limitations nor an engine swap explains them without evidence. Native Ghostty is a useful same-device reference, not a promise of physical native latency over a WAN.

## Reading and ratifying this proposal

**H** = proposed hard minimum outcome; **P** = provisional, hardware-calibrated performance target; **E** = evaluated interoperability, not an additional mandatory protocol. **L** = isolated Linux headless browser + real PTY evidence; **R** = real foreground Mac and PC, with exact OS/browser/display/input configuration recorded. Every row below specifies both; L cannot substitute for R. All checks are **future acceptance**, not completed tests or benchmark results.

Current-state labels mean **source** (code/documented mechanism exists, not end-to-end proof), **reported defect**, **absent in inspected integration**, **unknown**, or **platform policy**. An upstream engine feature is not automatically a Manifold feature. Ratification must settle the target Mac/PC browsers and programs, the authority choice in #204, transfer semantics and retention, supported Unicode/input corpus, and performance reference conditions. No proposed number is a release gate until calibrated and approved.

### Program neutrality

The product is a terminal, not a frontend for one CLI agent. Its core contract serves arbitrary authorized terminal workloads through standard terminal behavior and generic capabilities. Shells, editors, build/log producers, CLI agents and multiplexers are compatibility examples, not architectural owners. Image support is conditional on the consuming application's actual capabilities: no claim is made that every program can decode images or accept attachments.

Acquire clipboard/file bytes in the browser, transfer them to the authorized target machine through a generic capability, and let a supported consumer use the result. An application-specific attachment adapter may improve interoperability after that foundation exists; it must remain optional and must not become a special backend or per-application file-transfer protocol. Terminal image display and clipboard image input remain separate decisions.

## Ghostty-class experience: what should feel right

The aim is not to reproduce a native terminal's settings menu or check protocol boxes. It is to remove the small interruptions that make sustained terminal work feel second-class. Organize ratification in three layers:

- **Must feel right:** typing, crisp readable output, smooth resizing, predictable focus/selection/paste, stable history and recovery, and control that another view cannot accidentally steal. These are the hard outcomes below, even when several integration layers must cooperate.
- **Essential capabilities:** text/image/file workflows, selection/copy, search, safe links, navigable history and accessible keyboard operation. A capability is complete only when the intended program or remote filesystem receives the actual content; an attractive UI alone does not count.
- **Worthwhile extensions:** the proactive inventory below. These are candidates for operator prioritization, **not additional ratified mandatory features**. Favor small, trustworthy workflow improvements over accumulating escape-protocol support or settings.

### Clipboard and path boundaries from source audits

These are source/platform findings [S5, S6], not completed browser or native-workflow tests:

- A focused DOM paste event can expose image/file items, but current xterm text paste reads only `text/plain`. Preserve its text/bracketed-paste and IME behavior; intercept an image/file gesture only when positively handling its payload. Image data does not arrive through xterm's separate non-UTF-8 `onBinary` input API.
- Event-time clipboard data and `navigator.clipboard.read()` are different mechanisms. Async reads require a secure context and browser-specific activation/permission behavior; image formats and file-manager clipboard representations vary by OS/browser. Do not promise arbitrary MIME availability, global shortcut capture or background clipboard reads. Explicit paste/attach controls and picker fallbacks must report their own permission limits.
- Browser `File` data provides bytes and metadata, not an authoritative local absolute path. File inputs intentionally hide that path (often `C:\fakepath\…`); dropped file bytes are read at `drop`, not during protected drag phases. A client pathname cannot identify a remote file. Keep external-file gestures separate from internal pane/layout drag-and-drop.
- Native terminals/editors may insert a host-readable, shell-quoted path through privileged filesystem integration. The browser equivalent first needs verified placement on the correct authorized machine. Offer remote-path copy or explicit insertion only after completion, with consumer-appropriate quoting, no automatic Enter and no auto-execution; never assume the focused program is a POSIX shell.
- Native clipboard readers, optional MIME clipboard protocols such as OSC 5522, and application attachment handling can explain a native workflow without establishing browser support. Protocol negotiation, permissions and multiplexer behavior require separate compatibility evidence. OSC 52 text clipboard and terminal image-display protocols are not generic upload/download services.

## Response and performance: proposed budgets, not measurements

At actual foreground refresh rate `f`, `F = 1000/f` ms (60 Hz: 16.67; 120 Hz: 8.33; 144 Hz: 6.94). Hardware, browser, font/grid, renderer, workload and topology must be fixed per comparison. These **P** rows never turn correctness failures into acceptable percentiles.

WAN conditions need a separately calibrated budget accounting for measured transport delay; these frame counts cannot erase RTT. Separately measure input send → returned echo parser completion and next rAF. These are not physical input-to-photon guarantees. | **L:** explicit event/send/echo/parser/rAF timestamps; label synthetic input and Event Timing availability. **R:** physical keyboard, trusted Event Timing where available (8 ms rounding), loaded/idle trials; calibrated high-speed camera/photodiode only if claiming photons [S4].                                                                                    |
| P3 P — frame health           | Foreground resize/loaded-interaction rAF interval p95 **≤2F**; report count/max above **3F**, LoAF/long-task diagnostics and input stalls. No foreground FPS promise for hidden/background tabs.                                                                                                                                                                                                                                             | **L:** rAF distribution and optional Chromium LoAF attribution, unsupported APIs named. **R:** real GPU/browser/display trials, visible frame inspection; background/suspend recovery separately under C5/C6.                                                                                                                                                             |
| P4 H/P — throughput/resources | **H:** bounded workload completes with expected final state and no silent corruption; input/cancel and other panes remain usable. **P:** no universal bytes/s target until device-specific baselines exist; approve a noise-aware regression envelope, including memory/queue drain and 1/2/4/8 active or hidden terminals.                                                                                                                  | **L:** record producer, PTY ingress, mirror/browser parser completion, queues/resources and final screen separately for text/ANSI/Unicode/TUI workloads. **R:** interleaved repeated same-device native/browser workloads, foreground and hidden cases, native local PTY and remote topology reported separately. Sink benchmarks do not prove displayed throughput [S4]. |

Measurement record: source commit, OS/browser/runtime versions, hardware/GPU/driver, refresh/scaling/DPR/zoom, power mode, exact font/grid/content box, engine/addons, topology/RTT, workload hash, warm-up, raw samples, completed/failed counts, p50/p95/max and limitations. Start with 10 warm-ups, 30 independent input/resize trials and five sustained-output repetitions per condition; report timeouts/errors, do not discard them. Compare only same-clock intervals or explicit round trips; never subtract unsynchronized Mac/PC timestamps.

Keep endpoints distinct: producer finished → PTY ingress → mirror parser watermark → transport arrival → browser parser callback → DOM/geometry → rAF/render opportunity → physical display. `write` completion, DOM mutation, rAF and LoAF are **not photons**. WAN adds transport delay; isolate it rather than promise native physical parity or excuse local defects. Linux headless/software GPU can establish functional evidence and its own timings, not real Mac/PC latency or compositor quality [S4].

## Small operator testcard

1. **First supply examples, not secrets:** exact Mac/PC browser + OS; native terminal name; versions of selected shells, editors, build/log producers and interactive programs, plus a short example of an image/file workflow that works natively. Identify where each consumer runs (local, SSH or another machine), whether a multiplexer is involved, and which browser/terminal pane exhibited each defect. No access tokens or clipboard contents are needed.
2. Use an isolated development terminal and generated numbered text, one synthetic image and a harmless file. Record display refresh/scaling, browser zoom, font size/grid and network topology. Keep native and browser comparisons on the same device; label remote conditions separately.
3. In each browser: text paste; generated image → authorized remote machine → actual image-aware consumer decode/attachment where supported; file → remote destination and retrieval; selection/copy; link/search/history; actual IME if used. Record **worked / explicit refusal / silent loss / not available** separately for transfer and consumption, with receiver evidence rather than an apparent pasted path.
4. With both devices viewing the same test PTY: alternate then simultaneous resize/zoom, note visible authority, reload/disconnect/rejoin during numbered output. Retain a short private/redacted screenshot or recording only if safe; never publish sensitive terminal output. Missing recording does not invalidate the original report.
5. Provide observed outcomes and environment, not a request for a production token. Mark untested combinations as untested. Ratification chooses desired behavior and calibrated budgets; it does not retroactively certify implementation.
