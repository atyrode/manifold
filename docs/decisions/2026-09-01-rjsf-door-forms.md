# Generate door-invocation forms with react-jsonschema-form (rjsf), not JSON Forms

**Date:** 2026-09-01  
**Status:** Accepted (#128, #131 item 6)

## Context

Every composed action publishes its input as JSON Schema — `GET /api/protocol`'s `actions`
block and each roster row's `actions` carry the SAME `ActionSummary` objects, generated by
`z.toJSONSchema` from the very zod definitions the dispatcher validates with. A door-form
surface (first host: the F10 inspector's pinned card) must render argument forms FROM those
schemas; hand-rolled schema-walking form code is ruled out by #128 itself, and would be a
second interpreter of a vocabulary the wire already interprets once.

Two credible generators exist. Invariant 8 demands the evaluation on record.

## Candidates, evaluated 2026-09-01

Facts measured on this machine (react 19.2.8, `renderToStaticMarkup` against a real
published action input schema: bounded strings, optional boolean, enum, and zod 4's
`$schema: …/draft/2020-12/schema` header; bundle = `bun build --minify`, react external,
gzipped):

|                                | rjsf 6.8.0                                                        | JSON Forms 3.8.0                                                                                                                                                       |
| ------------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| License                        | Apache-2.0                                                        | MIT                                                                                                                                                                    |
| Packages needed                | `@rjsf/core`, `@rjsf/utils`, `@rjsf/validator-ajv8`               | `@jsonforms/core`, `@jsonforms/react`, `@jsonforms/vanilla-renderers`                                                                                                  |
| Draft 2020-12 (what zod emits) | one-liner: `customizeValidator({ AjvClass: Ajv2020 })`            | default validator THROWS on the published `$schema`; needs a hand-built ajv                                                                                            |
| Renders the real schema        | yes — labels, required marks, typed inputs, enum select           | yes, once given the custom ajv; shows validation errors before first touch                                                                                             |
| Commit point                   | a real `<form>` with submit; `onSubmit` hands over validated data | no submit concept — continuous `onChange`, commit wiring is ours to hand-roll                                                                                          |
| Bundle (min / gzip)            | 416 KB / 138 KB                                                   | 268 KB / 86 KB                                                                                                                                                         |
| Call-site vocabulary           | `schema`, `validator`, `onSubmit`                                 | `renderers`, `cells` — `renderer` is canon for a discipline renderer (S11's law: one word per concept), so every call site would re-use the word for a foreign concept |

## Decision

**rjsf, Apache-2.0, pinned exact:** `@rjsf/core` 6.8.0, `@rjsf/utils` 6.8.0,
`@rjsf/validator-ajv8` 6.8.0, plus `ajv` 8.20.0 (already the validator's own engine;
named directly only for the `Ajv2020` class). Dependencies of `@manifold-plugin/debug`,
NOT of the floor: the door-form surface is core.debug's inspector card (#128 names it),
S2 already lets a plugin carry its own npm dependencies, and the engine's line budget
(S16) is priced for mechanism, not for a form library. Loaded lazily, so the workspace
bundle pays nothing until an inspector actually pins a node.

Three verdicts carried the day, in order:

1. **The published dialect is not optional.** zod 4 stamps every action schema
   draft 2020-12. rjsf supports that dialect as a documented configuration of its own
   validator package; JSON Forms' default path rejects our schemas outright, and the
   escape hatch is assembling the validation engine ourselves — adopting a library plus
   owning the part of it that failed.
2. **A door fires at a commit point** (the plane rule): rjsf's submit IS the commit
   gesture, validated data in hand. JSON Forms' continuous-change model would make us
   hand-write exactly the commit wiring the adoption exists to avoid.
3. **Generation is the design center.** rjsf renders from the schema alone; JSON Forms'
   center of gravity is authored uischemas, which this repo will never write — the schema
   arrives off the wire, or the form is wrong.

The ~52 KB gzip advantage of JSON Forms is real and recorded; it does not outweigh 1–3,
and lazy loading keeps either candidate off the boot path. The lexicon collision (its
API forces `renderers`/`cells` identifiers at every call site) is a repo-specific cost
the gate would make permanent. rjsf's own "widgets" vocabulary — a banned synonym — never
appears for generated default forms, and none may be introduced: customizing rjsf beyond
templates would put the banned word in an identifier and fail S11, which is an acceptable
fence around a customization we do not want anyway.

## Consequences

- `@manifold-plugin/debug` gains four exact-pinned dependencies; upgrades are deliberate.
- The form's skin is element-scoped under core.debug's own `door-form` family — rjsf's
  emitted class vocabulary is deliberately NOT registered in `cssFamilies`, so no sheet
  may anchor on it and the library's markup remains an internals detail (S13).
- A second consumer of generated forms is the trigger to promote the wrapper toward the
  stdlib, with the budget extraction that requires — recorded here so the promotion is a
  decision, not a drift.
