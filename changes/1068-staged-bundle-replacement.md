A hub can now cross to a new plugin protocol together with the installed plugins that protocol would hold. The deployment stages whole replacement bundles for the same plugin ids, each pinned by digest, and the new hub installs them at startup, before it serves or wires native execution. Grants, installer lineage, enablement and plugin data carry over. A replacement that widens capabilities, changes the data major, carries an unknown or future stamp, or would leave another bundle held is refused, and a refusal changes nothing. When a replacement changes a plugin's native declaration, the operator must acknowledge it. That plugin's native deployments are then stopped at their approved revision until the deployment review admits the new one, and the preview owner is not pinned while any of them, or a service they provide, still waits. A crossing interrupted by a crash resumes at the next start. Sending the same deployment again after it completed changes nothing, so deployments reviewed since stay as reviewed. The crossing is forward-only. If the switch or its live verification fails, the same deployment restores the previous hub with its previous bundles and re-enables exactly the stopped deployments, and it refuses if a plugin was reinstalled since, even with the same bundle. A manual rollback to a version before a completed crossing is refused before anything stops, because recovery after a completed crossing is a forward deployment. `docs/SELF-HOST.md` §Environments describes the procedure.
